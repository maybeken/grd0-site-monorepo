# Taste
- Requires British English spelling and phrasing (e.g. behaviour, colour, initialise, licence) in code, comments, documentation, and commit messages. Confidence: 0.9
- Wants non-trivial changes (e.g. dependency upgrades) done on a dedicated new git branch rather than directly on the current/main branch. Confidence: 0.6
- When creating a new branch, expects the branch to start from up-to-date remote main: fetch origin and rebase onto origin/main before beginning work. Confidence: 0.8
- Favors moving dependencies to the latest versions, including major bumps, accepting that code fixes/breakage follow. Confidence: 0.5
- When asking to "stage the changes made," expects staging scoped to the current session's work — unrelated pre-existing working-tree edits and untracked build artifacts/binary outputs left out. Confidence: 0.5
- Prefers staging changes for review without immediately committing. Confidence: 0.4
- Works in explicit increments — stage, then commit, then push — and expects work committed locally to be pushed to origin on the feature branch with its upstream set, not left local. Confidence: 0.6
- Expects the written spec/design artifacts (OpenSpec `specs/`, `design.md`, `proposal.md`, `tasks.md`) to be refreshed to match what was actually delivered as the closing step of a feature — "update the specs with latest changes" — before committing, rather than leaving them describing the original plan. The request is typically a one-liner ("update the spec with the new changes", "update the specs related to this, or the barest update the specs with no hint of which files or behaviour changed") expected to propagate across every artifact — spec requirements/scenarios, `design.md`, `proposal.md`, and new checked-off items in `tasks.md` — not just the spec file, and across every *related* living spec that describes the affected behaviour (e.g. both `specs/article-editor/` and `specs/article/`), not only the one whose requirement was directly edited. Confidence: 0.78
- Prefers Vue over React for frontend work; questions React-based solutions and asks whether they can be done as a Vue project instead. Confidence: 0.5
- Expects a single, non-duplicated taste/memory store and will question redundant or oddly nested files in the agent's config directory. Confidence: 0.3
- Wants the agent's taste/memory files version-controlled and committed into the repository (e.g. `git add .commandcode/taste/...`), not left untracked or gitignored. Confidence: 0.55
- Will ask for small docs/config chores (switching to main, updating README, committing agent config) to be done directly on `main`, in contrast to feature work on a dedicated branch. Confidence: 0.45
- Expects repository documentation such as README (structure listing, setup steps) kept in sync with structural changes like adding or renaming a package. Confidence: 0.4
- Strongly prefers composing new features from what already exists — existing libraries, existing components, existing iframes/embeds — and states reuse explicitly in feature requests ("using existing library", "using existing component", "using existing iframe", "reuse the component in article editor") rather than accepting a rewrite or custom implementation. When a new surface needs a capability another area already ships, he names the existing component to import and expects that shared component wired in (even across feature boundaries, e.g. an article-editor picker used inside a music playlist form), not a parallel lookalike. Confidence: 0.85
- Prefers new features shipped as a parallel, additive implementation (new entity, new routes, new editor) that leaves the existing working feature untouched, then replaces it in-place only once the new one is proven — explicitly rejects "evolve the existing model" approaches for big changes. Confidence: 0.65
- Prefers large payloads (e.g. drawing/scene JSON) stored as separate files on the backend with the database holding only a path/reference to them, rather than inlining blobs into database rows/JSON columns. Confidence: 0.65
- Expects storage access to go through an abstraction with the local filesystem as the default implementation and object storage (S3) as a drop-in future backend, even before S3 is needed — designs for later extensibility rather than hard-coding one backend. Confidence: 0.6
- Prefers resources created as an empty container first, with dependent content attached afterwards ("the flow should create an empty article for edit") rather than content existing before its parent. Confidence: 0.5
- Prefers new content to default to an unpublished/draft state, requiring an explicit publish step to make it public. Confidence: 0.5
- Expects a dual identity scheme: an immutable UUID used internally for storage and references plus a human-readable URI/slug, but routes/API calls should address resources by URI not UUID — chose URI for all API calls once offered the choice. Confidence: 0.7
- Accepts that renaming a slug/URI breaks old links — explicitly declines alias tables or redirects ("once URI is renamed, no redirect is needed") in favour of the simpler unique-URI model. Confidence: 0.55
- Wants uniqueness/duplicate prevention enforced in application logic ("soft logic") that accounts for soft-deleted rows, with the DB unique index as a backstop rather than as the only guard. Confidence: 0.55
- Prefers strict, explicit failure over implicit convenience on conflicting operations: a create that would collide with an existing resource must be rejected (e.g. 409 Conflict) rather than idempotently returning the existing resource ("open-or-create"). Confidence: 0.5
- Comfortable approving a plan with a terse "go ahead" once the approach has been laid out, and expects the agent to first produce written spec/design artifacts (proposal + design + specs + task breakdown, e.g. via OpenSpec) before any implementation code is written. Confidence: 0.6
- Drives implementation through the OpenSpec workflow end to end: writes the change artifacts first, then kicks off coding by invoking the apply command as a bare slash command (`/openspec-apply-change`, `/opsx-apply`) with no arguments or extra instructions rather than restating the plan, expecting the agent to pick the in-flight change itself and track progress against that change's `tasks.md` checklist. Confidence: 0.7
- Opens an exploration/planning session the same bare-command way — `/opsx-explore` with no question or topic attached — expecting the agent to orient itself from repo state (OpenSpec change/spec lists, `openspec/config.yaml`, `git status`/diff, recent archived change proposals) and then surface a few concrete threads with the consequences named, rather than asking what to explore or starting work. Confidence: 0.35
- Expects the lifecycle to close by archiving the finished change, immediately after the agent reports implementation complete (invoked as a bare slash command with no arguments or restated context — `/openspec-archive-change`, `/opsx-archive`, etc.) — syncing delta specs into main `openspec/specs/` and moving the change under `openspec/changes/archive/<date>-<change>` — rather than leaving completed changes active. Confidence: 0.75
- Prefers to close a change out rather than leave it open for residual manual verification: when the only unticked task is a manual check he has not run (e.g. a browser render check), he has it marked done and the change archived, rather than keeping the change active until the check is performed. Confidence: 0.35
- Answers only the open decisions an agent raises and otherwise lets proposed defaults stand, rather than restating or re-approving every detail. Confidence: 0.45
- Wants to be able to exercise the app locally without real infrastructure: asks for dev-only escape hatches (e.g. bypassing authentication when the running environment is "LOCAL") so features can be tested end to end on their own machine. Confidence: 0.55
- Prefers environment detection encapsulated in a single named helper driven by an explicit environment variable (a function answering "is this LOCAL?"), so the same check can be reused across backend and frontend instead of ad-hoc conditionals. Confidence: 0.5
- Prefers editors with a persistent, always-visible side-by-side preview (editor left, preview right on wide screens, stacking below on small ones) instead of a toggle/hide button, with the preview refreshed on a debounce (~3s after the last edit) rather than re-rendering on every keystroke; opening or saving refreshes it immediately. Confidence: 0.45
- Prefers primary/terminal actions (save button, add-block palette) placed at the end of the content flow, below the last block, rather than above the block list. Confidence: 0.5
- Prefers a single full-width editing surface per block; rejects split half-width "editor + separate inline preview" panes — previewing is the job of one global preview pane, not of each block editor. Confidence: 0.5
- Reports bugs as terse, symptom-only statements (e.g. "the content is not rendered in the public article screen", "delete does not work currently", "it seems to be switching back to read-only mode only after first interaction", "the player is not showing", "it is not returning the first image", "the url seems to be wrong") and expects the agent to investigate the root cause end to end against the running app — inspecting stored data, hitting the live API, reading the relevant code — rather than come back with clarifying questions. Evidence is usually pasted raw as the offending rendered markup/DOM (the exact `<img>` with its `src`/`srcset`) or the literal broken value, with no analysis attached; reading the wrong output closely (e.g. spotting `%2520` double-encoding) is on the agent. Confidence: 0.73
- Expects the host app, not an embedded third-party widget (e.g. the Excalidraw iframe), to own global keyboard shortcuts: embedded editors must be stopped from capturing combinations like Ctrl/Cmd+S and should forward/delegate them to the parent app instead. Confidence: 0.55
- Expects embedded interactive canvases/iframes (e.g. Excalidraw) not to hijack page scrolling: wheel/trackpad events must scroll the page until the reader deliberately clicks to activate the embed, with an unobtrusive "click to interact" hint so the behaviour is discoverable. Confidence: 0.55
- Expects a read-only/view mode to be authoritative from the very first render and stay that way — the embedded widget's restored saved state must not override it or leave the content briefly editable. Confidence: 0.45
- Prefers non-blocking in-app toast notifications over native browser `alert()` dialogs for success/error feedback, and expects a single shared toast mechanism reused across the app rather than per-component feedback. Confidence: 0.6
- Expects the viewport to follow the item being manipulated: after reordering/moving a block, the page should scroll the moved block into view (smooth, centred) instead of leaving the user looking at its old position. Confidence: 0.5
- Expects per-package/per-directory READMEs (e.g. `api/README.md`, `vue-web/README.md`) to be kept accurate too, not just the root README — asks for updates "in other directories as well" and wants stale commands/env vars/notes refreshed rather than a root-only edit. Confidence: 0.6
- States feature requests as a single terse, sometimes typo-ridden sentence naming only the desired UI element and its placement ("add a button next to publish date in editor to publish now", "create an animated background that simulates particles flying though the screen randomly"), and expects the agent to build the whole thing — markup, handler logic, translation keys, feedback toast, type-check/build verification — without coming back with clarifying questions. Confidence: 0.6
- Prefers a combined admin "list + editor on one page" screen split into two distinct route-addressed pages: a listing page and a separate editing workspace addressed by the resource's URI, so opening an item is navigation rather than local `selected` state. Confidence: 0.5
- Expects long admin lists to be paginated rather than fetched whole, and accepts changing the API contract (server-side `page`/`page_size`/`total` envelope, reusing whatever pagination helper the codebase already has) to get it. Confidence: 0.45
- Expects an editing live-preview pane to be scroll-synchronised with the blocks being edited, aligned by block identity rather than proportional scroll position, and one-way (the editor drives the preview; scrolling the preview never moves the editor). Confidence: 0.5
- Prefers document metadata and actions (URI, publish date/status, public link, delete) grouped in a dedicated sidebar panel alongside the editor, rather than interleaved into the editing surface. Confidence: 0.45
- Prefers new work captured as its own OpenSpec change directory rather than folded into an existing in-flight change. Confidence: 0.4
- Expects OpenSpec specs left validator-clean: an over-long combined requirement that trips the `openspec validate` length warning should be split into separate focused requirements (e.g. summary derivation / cover derivation / cover persistence) with their scenarios re-attached, and the result re-validated (`openspec validate --all`) with the pass count reported rather than the spec left merely "parses fine". Confidence: 0.35
- Prefers decorative background animation sparse and restrained — a handful of elements (single digits to low teens) with randomised, staggered appearance and slow fading trails (~5s decay) rather than dense, uniformly-populated effects; refines these looks by handing over concrete numeric parameters (count range, delay, decay time, opacity/transparency) in one terse line. Confidence: 0.5
- Expects decorative motion trails to have a per-element lifecycle: the trail stays fully intact while its element is still on screen and only begins fading once that element has left the viewport (then expiring after the stated duration, e.g. 5s), rather than a globally decaying trail buffer that fades the whole canvas uniformly. Confidence: 0.4
- Expects decorative background elements to enter the scene from off-screen — spawning just outside a randomly chosen screen edge and travelling inward — rather than materialising in the middle of the viewport. Confidence: 0.35
- Wants decorative background effects kept visually subordinate to content: dimmed/frosted behind the page (e.g. a semi-transparent black overlay with blur above the canvas) so foreground text stays crisp and readable, with the overlay stacked below content and marked `aria-hidden`/non-interactive. Confidence: 0.4
- Expects the agent to operate the local running stack itself: a terse imperative like "restart the backend app" / "kill and restart the running backend app" / "restart the running backend process" (typos and all) means find the listening process, rebuild the binary, stop the stale process, relaunch with the same environment (repo env file / inherited env), then verify health and real data — not just instructions for the user to run. When the agent hands over manual run commands for the user's own verification, he may still come straight back with "kill and restart the running backend app", and after a code change he asks for the running process to be restarted so the change takes effect, so taking ownership of process lifecycle (find the PID, rebuild, kill, relaunch in the background) is the expected default rather than an offer. Confidence: 0.65
- Prefers status indicators (publish state, save/unsaved state) rendered as plain muted text rather than button/pill/bordered-badge shapes, and grouped with the action controls on the right-hand side of the editor top bar instead of floating loose on the left. Confidence: 0.45

Confidence: 0.5
