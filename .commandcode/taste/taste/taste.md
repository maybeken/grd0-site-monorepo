- Expects the written spec/design artifacts (OpenSpec `specs/`, `design.md`, `proposal.md`, `tasks.md`) to be refreshed to match what was actually delivered as the closing step of a feature — "update the specs with latest changes" — before committing, rather than leaving them describing the original plan. The request is typically a one-liner ("update the spec with the new changes", "update the spec and design if there is any undocumented changes made in this conversation", "update the specs related to this, or the barest update the specs with no hint of which files or behaviour changed", "update spec and design for latest changes") expected to propagate across every artifact — spec requirements/scenarios, `design.md`, `proposal.md`, and new checked-off items in `tasks.md` — not just the spec file, and across every *related* living spec that describes the affected behaviour (e.g. both `specs/article-editor/` and `specs/article/`), not only the one whose requirement was directly edited. It is not a once-at-the-end ritual: the same one-liner recurs after each small refinement mid-change (e.g. a breakpoint tweak landing, then "update spec and design for latest changes"), and the named artifacts ("spec and design") are the ones to bring into line, with the result re-validated (`openspec validate <change> --strict`) and existing task progress confirmed rather than re-ticked. The conditional phrasing ("if there is any undocumented changes") means an audit pass, not a mechanical diff of the known edits: grep the artifacts for both missing behaviour and stale/superseded text — old migration steps, resolved open questions, wrong claims about test coverage or fallbacks, removed features — and fix whichever drifted, then re-validate.
