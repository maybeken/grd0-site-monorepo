# Design

## Context

See `proposal.md` for motivation. The gallery's read path is split across two stores: `api/data/files/files.json` (generated by `assets-helper`, consumed at runtime for the asset list) and SQLite (collection metadata and per-image overrides). The public gallery uses `GetAssetV2` for paginated assets and `GetGalleryCollection` for collection metadata.

Two constraints shape the approach:

- `GetAssetV2("all")` filters directories against existing collection rows, so directories without metadata are invisible to any client today.
- The renderer (`GalleryCard.vue`) falls back to the wildcard row at row level: if a detail row exists for a filename it is used whole; otherwise the `*` row is used whole. Fields are never merged, which is why overrides must start from the defaults.

Detail rows are stored with `path` equal to `/gallery/<directory>` while collection rows are keyed by the bare directory name. The existing detail endpoints take `:path` and are addressed by appending that stored path, which produces the double slash seen in production requests.

## Goals / Non-Goals

**Goals:**

- One admin read endpoint that exposes asset directories and counts, so adoption and the listing share a single data source.
- A workspace that treats `files.json` as the source of truth for which assets exist and SQLite as the source of truth for overrides.
- Keep the existing public read path and its endpoints untouched.
- Reuse the article editor's gallery picker and the existing editor shell conventions.

**Non-Goals:**

- Asset upload, moves, or deletion.
- Changing `GalleryDetail` or `GalleryCollectionDetail` schemas.
- Changing how the public gallery renders overrides.
- Editing EXIF data.

## Decisions

**1. Add one admin directory endpoint rather than changing the asset endpoints**

`GET /gallery/directories` (inside `restrictV1`) reads `files.json` through `data.ReadAsset()` and returns each `/gallery/*` directory with its bare name, stored key, and asset count. The editor merges this with `GET /gallery/collection` to split directories into collections and adoptable directories.

Alternatives considered:

- *Derive directories client-side from `/gallery/all`*: rejected because that endpoint filters against existing collection rows, so orphans never appear.
- *Add a generic unpaginated asset listing*: rejected as a larger contract change for the same information.
- *Scan page by page until no assets remain*: rejected as unbounded and unable to reveal directories with zero rows.

**2. Collection identity in the route is the bare directory name**

Routes use `/editor/gallery/:collection`, where the parameter is the bare name (`new zealand`). The service owns the translation to the stored detail path: `detailPath(collection) = "/gallery/" + collection`. Detail requests use the same construction the public client already relies on, isolated in one function so the double-slash convention is not spread through views.

Alternatives considered:

- *Use the stored `/gallery/<name>` path as the route parameter*: rejected because router params cannot carry slashes without catch-all routes, and the leading slash is an API storage detail.
- *Change the API to take a bare name on detail routes*: rejected as unnecessary churn; the existing contract works and is exercised in production.

**3. The workspace joins paginated assets with all override rows**

Assets are read page by page through `loadMoreAssets(collection, page)` (40 per page). Overrides are read from `GET /v2/gallery/details/<storedPath>` with `page_size=200`, looping until `total_pages` is exhausted, then indexed by filename. This keeps the asset page size aligned with the public gallery while fetching the comparatively small override set once.

Alternatives considered:

- *Fetch details per asset page*: rejected because it repeats requests and still requires all rows for the stale-override check.
- *Add an unpaginated override endpoint*: unnecessary while `page_size=200` plus a loop bounds the request count.

**4. Pending changes are accumulated and saved explicitly**

The view keeps a pending map keyed by filename containing the desired description and timezone adjustment, independent of the currently loaded page. Dirty state is derived from the pending map, so pagination does not discard edits and `useUnsavedGuard` can protect navigation. Saving upserts each pending row and deletes rows whose both fields were cleared, then reloads.

Alternatives considered:

- *Per-row auto-save*: simpler but discards the established explicit-save and unsaved-guard behaviour, and makes it harder to revert a mis-edit.
- *Save only the visible page*: rejected because it silently loses edits made on other pages.

**5. Overrides start from the collection defaults**

Because the renderer does not merge fields, creating a row for an image replaces the wildcard values for that image entirely. The row editor therefore pre-fills description and timezone from the wildcard row when no override exists, so the author does not accidentally drop the timezone correction. Clearing both fields removes the row and restores inheritance.

**6. Cover selection reuses `GalleryPicker`**

`GalleryPicker` gains an optional `collection` prop. When supplied, the collection selector is hidden and assets are loaded for that collection only. This mirrors how `PlaylistForm` reuses the article editor's `MusicPicker` rather than duplicating an asset browser.

**7. Adoption creates metadata only**

Adoption upserts a `GalleryCollectionDetail` with `path` set to the bare directory name and an empty title and cover. No asset is touched. Deleting a collection removes only that row; the design deliberately leaves overrides in place and reports the consequence in the confirmation text.

## Risks / Trade-offs

- **The detail path convention is fragile** → Isolate it in one `galleryDetailPath` helper and add an integration task that exercises collection load and save against the running API. A future API cleanup can replace the helper without touching views.
- **Large collections produce many override rows** → Assets stay at 40 per page, overrides use the 200 maximum plus a bounded loop, and pending state is a map rather than a full copy.
- **Clearing fields deletes a row, which is irreversible in the UI** → Deletion only happens on explicit save, dirty state is visible, and the unsaved guard covers navigation.
- **Adopting a directory with a poor name publishes a collection with a bare-name title** → Adoption keeps the author on the listing with the new row visible, and the workspace is one click away for renaming.
- **Stale override detection depends on `files.json` freshness** → It uses the same runtime index as the public gallery, so it can only report what the public gallery would also see.
- **Two editor changes touch `editor-console`** → This change lands first and adds only the Gallery entry; the traveler's map change extends the same sidebar requirement afterwards.

## Migration Plan

No schema or data migration. Deployment is a normal API and web build. Rollback removes the routes and the directory endpoint; existing rows are untouched by the feature.
